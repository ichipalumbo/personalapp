## 3. Quais escritas do laço podem trazer `gcalSyncFailed` e como confirmei

As três operações que escrevem em `/api/agendamentos` são as que podem retornar o corpo do backend com `gcalSyncFailed: true`:

- `POST` em `resCriar` no bloco de criação de agendamento.
- `PUT` em `resAtualizar` no bloco de atualização de agendamento.
- `DELETE` em `resExcluir` no bloco de remoção remota.

Confirmei isso pela leitura do laço interno em `_sincronizarAgendamentosViaCRUD` e pela natureza do backend: o MongoDB grava e a API do Google falha em um subset de operações, mas mantém o status HTTP em `200`. O caminho de sucesso real com falha parcial não é um erro de rede nem um `!ok`; ele é um `200 ok` com um corpo que inclui `gcalSyncFailed: true`.

## 4. Como mantive `_respostaVirtual` retrocompatível

Mantive a chamada antiga sem quebrar compatibilidade:

```js
function _respostaVirtual(status, extras = {}) {
    return {
        status,
        ok: status >= 200 && status < 300,
        ...extras
    };
}
```

Isso preserva o contrato antigo para `_sincronizarAlunosViaCRUD`, que chama `_respostaVirtual(200)` sem argumentos. O chamador de alunos continua recebendo `{ status: 200, ok: true }` e o novo campo extra só aparece quando a resposta do agendamento precisa propagar `gcalSyncFailed`.

## 6. Teste automatizado / mutação

Não havia harness de browser para `assets/js/storage.js` no repositório. Para testar esse caminho do frontend seria necessário:

- extrair a lógica de parse da resposta para um módulo reutilizável;
- montar um ambiente de browser ou jsdom para simular `fetch`/`Response`;
- ou refatorar a função para permitir injeção do objeto de resposta com payload sintético.

Isso é refatoração fora de escopo para essa correção, então optei por validação estática obrigatória e pela leitura do fluxo real do código. A regra de mutação não foi aplicada porque não existe teste automatizado compatível com arquivo front-end sem novo harness.

## 8. Confirmação de que o caminho de sucesso pleno não mudou

O caminho de sucesso pleno foi mantido intacto:

- `salvarDados()` continua retornando `{ ok: true, motivo: 'sucesso' }` quando não há `gcalSyncFailed`.
- O toast verde continua sendo exibido no fluxo normal.
- A mudança foi apenas a propagação informativa da flag quando o MongoDB gravou mas o Google falhou, e a exibição de um aviso de advertência em vez de transformar a operação em erro.
- Não alterei status HTTP, retry, fila, nem contrato de `apiFetchBackend`.
